# Repository Guidelines

## Project Structure & Module Organization

Project TOWER is a Godot 4.7 / GDScript 2D top-down action Roguelite. The main scene is `scenes/main.tscn`; `project.godot` contains the project and input settings. Open the project with Godot 4.7.2, the version used for the current MVP.

- `scenes/` contains the main scene and reusable player, enemy, and projectile scenes.
- `scripts/` contains the run and floor controllers, combat and enemy behavior, procedural arena visuals, audio, localization service, and UI. The UI is assembled by `scripts/game_ui.gd`.
- `data/game_data.gd` is the source of truth for enemy stats, floor waves, equipment effects, and lore placement.
- `localization/game.csv` holds the Simplified Chinese and US English text. Godot imports it into the adjacent `.translation` resources. Context and terminology live in `docs/localization/`.
- `assets/fonts/` contains the bundled Noto Sans SC font and its license. Other current visuals and sound effects are generated by project scripts.
- `tests/test_mvp.gd` is a standalone headless integration test. `docs/GDD.md` is the current design reference and links to module documents in `docs/design/`. `docs/QA.md` records validation and outstanding checks.
- `addons/godot_ai/` is the existing Godot AI editor integration, also referenced by the project autoload and editor-plugin settings. Avoid unrelated changes to the addon.

Godot generates `.godot/`; it, `/android/`, local `/builds/`, and the machine-specific `.codex/config.toml` are ignored by Git. Keep Godot's relevant `.uid`, `.import`, and imported translation metadata with the source files.

## Build, Test, and Development Commands

Run from the repository root with Godot 4.7.2 on `PATH`. On macOS, substitute `/Applications/Godot.app/Contents/MacOS/Godot` for `godot` if necessary.

- `godot --editor --path .` opens the project in the editor.
- `godot --headless --path . --import` imports resources and checks editor loading; it is a smoke check, not a test suite.
- `godot --headless --path . --script res://tests/test_mvp.gd` runs the standalone integration checks. Import first when resources have changed.
- `godot --path .` runs the configured main scene.

`export_presets.cfg` defines Windows x86_64 and universal macOS exports. Install matching Godot export templates first; see `README.md` for commands and signing limitations. Exported files under `builds/` are local artifacts, not source files.

## Coding Style & Naming Conventions

Use UTF-8 and LF line endings, as specified by `.editorconfig` and `.gitattributes`. Indent GDScript with tabs; use `snake_case` for files, functions, and variables, `PascalCase` for classes, and `UPPER_SNAKE_CASE` for constants. Prefer editing project settings through the Godot editor. No formatter or linter is configured.

Keep gameplay values in `data/game_data.gd` rather than duplicating them in UI copy. Player-facing text should use stable IDs in the translation CSV; update both languages, matching placeholders, and localization context when changing text. Preserve the bundled font's license and include appropriate licenses for any new third-party assets.

## Art and Audio Integration

When building a feature that will receive art or audio assets, reuse or add the scene resource slot or audio event it needs. Run the feature with a working placeholder driven by the same gameplay state or event the final asset will use. Keep gameplay timing and hit detection in gameplay code. Record the scene node or event ID, the relevant asset specs, and how to trigger it in-game in the feature notes or handoff list. See the [art and audio handoff guide](docs/design/v0.3/art-and-audio.md).

## Testing Guidelines

Run the headless import and integration test after relevant changes. Manually run affected gameplay or UI flows when practical, especially for input, visual layout, audio, and localization changes. The automated floor progression uses test-driven events and does not replace a complete human playthrough. Record material platform, export, and playtest limitations in `docs/QA.md`; Windows real-device testing and the target session length remain unverified.

## Commit & Pull Request Guidelines

Use concise, imperative commit subjects, such as `Add player movement`. Pull requests should describe the behavior changed, link relevant issues, and list checks performed. Include screenshots or recordings for visible changes, and call out changes to rendering or physics settings.
